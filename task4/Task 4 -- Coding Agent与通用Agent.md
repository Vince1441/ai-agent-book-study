# Task 4 -- Coding Agent与通用Agent

## 综合概述
1. 理解 Coding Agent 的基本工作方式，了解文件读取、代码搜索、代码修改、命令执行与结果反馈。
- Coding Agent的核心定位：代码是基础能力
    代码生成作为通用的问题解决方案，具有极高的精确性与灵活性，例如：数学推理可以通过代码生成来精准求解，业务规则使用代码进行表述远比自然语言阐述更加准确；当Agent缺乏工具时，可以通过代码生成临时编写一个。


- Coding Agent的七大核心工具：
    1. Code Interpreter（代码解释器）：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码即使在其中运行出错也不会影响到宿主机），安全执行python代码；
    2. Bash Shell（命令行终端）：在终端中执行命令，如运行测试用例、处理特殊格式文件
    3. 读文件工具：读取代码、配置、文档、日志等；
    4. 写文件工具：创建新文件或完全重写现有文件；
    5. 搜索文件名工具（Glob）：通过模式匹配快速定位文件系统中的目标文件，例如用 /*.py 找出项目中所有Python文件；
    6. 搜索文件内容工具（Grep）：在文件内容中搜索特定的文本模式、例如搜索所有调用了某个函数的代码行；

- 核心工具协同工作流：
     - **文件读取与搜索**：Agent 首先通过 Glob 和 Grep 快速定位目标文件或代码片段，再通过 Read File 获取上下文。
     - **代码修改与执行**：定位后，使用 Edit File 或 Write File 修改代码，随后调用 Bash Shell 或 Code Interpreter 运行命令或执行脚本。
     - **结果反馈**：执行后的输出结果（如报错信息、运行日志）会作为新的上下文反馈给 Agent，指导其进行下一步操作。




2. 理解 Coding Agent 的基本循环：Read → Think → Edit → Execute → Observe。
- Coding Agent的整体流程：
    1. 项目文档化（Read）：Agent通过系统性地阅读代码库，识别主要模块、核心抽象、组件间依赖关系，生成包含架构概览、目录结构、测试运行指南的初始文档。
    2. 任务理解与需求澄清（Think）：对于复杂需求，Agent 必须更加谨慎和有条理。  复杂性可能源于多个维度：
        - 需求本身的模糊性（用户知道想要什么但无法精确表达）、
        - 实现路径的多样性（多种技术方案可选，各有权衡）、
        - 影响范围的广泛性（需修改多个模块，可能破坏现有功能）。
        - Agent 应通过探索性调研来澄清边界，必要时主动与用户对话。
    3. 编写设计文档（Edit）：将抽象需求转化成具体实施计划，修改某些模块及修改原因，采用什么方案、架构会相对优势，预期对系统的影响；在进行大量代码生成前，先在概念层面验证方案的可行性。
    4. 代码实现与测试（Execute）:Agent遵循代码规范进行代码生成，编写完代码后，进行测试，视情况可能会进行多次“测试-修复”循环进行迭代；
    5. 审查与交付（Observe）：Agent对已生成的代码进行批判性审视，通过阅读代码、运行lint工具或调用专门的代码审查sub-agnet进行，如若发现问题则回到修改阶段进行修复，通过审查方可交付。





3. 理解文件系统在保存代码、数据和中间结果中的作用。
- 文件系统是信息流转的枢纽——记忆从文件读取，产物写入文件，经验也保存为文件。
- 以OpenClaw为例，在OpenClaw的设计中，文件系统不止是数据存储
- 它是 Agent 记忆、知识和能力的中枢。Agent 的长期记忆存储在 MEMORY.md（高层级事实和用户偏好）和按日期归档的 Markdown 日志中。更关键的是，Agent 拥有写文件的能力，这意味着它具备了修改自身外部产物的技术条件。当 Agent 首次执行，某个任务并发现了之前不知道的关键信息（例如给某银行打电话时，发现对方要求提供开户行地址才能验证身份），它可以先把发现写入记录。记录何时足以成为可靠知识、指令或程序，仍需结合更多轨迹与结果验证；



4. 理解通用 Agent 的基本设计，对比 Coding Agent 与通用 Agent 的任务范围和工具能力。
- 通用Agent的核心架构可以概括为：Coding Agent+文件系统

- Coding Agent与通用Agent的对比：
    - 任务范围：
        - Coding Agent：专注于任务理解、代码生成、修改测试、审查交付等软件工程任务。（基本循环：Read → Think → Edit → Execute → Observe）；
        - 通用Agent：在Coding Agent的基础上，增加了文件系统，通过文件系统丰富了记忆、知识管理与长期规划任务的能力。
    - 工具能力：
        - Coding Agent：依赖于七大核心编程工具 Code Interpreter（代码解释器）、Bash Shell（命令行终端）、读文件工具、写文件工具、编辑文件工具、搜索文件名工具（Glob）、搜索文件内容工具（Grep）；
        - 通用Agent：除了编程工具，还通过文件系统获得持久化记忆、跨会话状态保持的能力



5. 理解代码如何用于计算、数据处理、内容生成等非纯编程任务，以及 Agent 如何通过环境反馈持续完成复杂任务。
- 按“元能力作用对象”由内向外组织：
    1. **代码作为思考工具、思维本身**：用代码替代易出错的概率性思考。LLM 负责理解问题并写出代码，代码解释器负责符号计算与精确计算，实现协同。
    2. **代码作为业务规则约束**：代码化规则能防止不可逆的错误操作。通过“系统提示词 + 工具描述 checklist + 服务端代码化校验”提供三重保障。
    3. **代码驱动的多媒体生成**：利用 Slidev 框架生成 PPT，或通过 API 调用 Blender/FFmpeg 进行视频编辑。采用“提议者-审核者”机制，由 Vision LLM 审查渲染结果。
    4. **代码作为系统适配器**：遇到新数据格式时临时生成解析代码；自动分析执行日志，生成结构化报告并自动创建 GitHub Issue。
    5. **代码作为生成式UI**：动态生成含级联逻辑的表单、SQL 查询或 HTML 交付成果。安全策略将信任边界下移到数据层（如行级安全 RLS）。 
    6. **代码创造代码：Agent自举**：通过复制高质量 Agent 实现并进行针对性修改，实现“用代码修复和创造同类 Agent”的元编程循环。

- Agent通过环境反馈持续完成复杂任务：
    - **即时语法反馈**：文件写入后自动运行 linter/语法检查器，实现“编辑即验证”。 
    - **上下文精细化管理**：按行号范围读取文件，对命令输出进行截断与持久化，避免上下文溢出。
    - **动态状态注入**：通过 Agent 状态栏技术动态注入环境信息，使 Agent 始终感知当前系统状态



## 自测问题
1. 能生成一段代码的聊天助手，与 Coding Agent 的关键区别是什么？
- 关键区别：能否与真实执行环境交互，能否通过反馈自行完成任务；
- 聊天助手主要生成代码文本，用户需视作使用手册去自己复制、保存、运行和调试。Coding Agent 则能够读取实际项目文件、调用工具修改文件、执行代码、观察错误并迭代修复。因此，判断是否具备 Coding Agent 能力，不能只看能否写出正确代码，而要看能否形成基本循坏：Read → Think → Edit → Execute → Observe



2. “文件写入成功”“程序能运行”“用户需求已满足”，为什么是三种不同的判断？
- “文件写入成功”：只能视作文件已经写到指定位置，不能证明代码是否正确
- “程序能运行"：至少某种执行路径可以运行，不能证明功能是否完善，符合用户需求；
- ”用户需求已满足“：对照验收标准，结果达成目标，仍需进行审查环节，考虑未覆盖风险与交付条件



3. 为什么说代码可以是“创造新工具的工具”？请举一个非编程任务的例子。
- 因为代码具有通用性、可执行性和可组合性。Agent 可以根据新任务需求，生成原先不存在的程序工具，并将其变成可复用工具。
- 例如，用户要求：把200份不同格式的电商商品报价表统一整理，计算每个商品的利润率，输出排行榜。
    Agent生成程序工具：
    读取用户提交的各份报价表
    ↓
    识别与统一字段
    ↓
    清洗错误数据
    ↓
    计算利润率
    ↓
    按利润率排序
    ↓
    生成 Excel 或图表
- 任务完成以后，经过验证的代码还可以保存下来，为下一次类似任务复用。



4. 如果 Agent 连续修改三次仍然测试失败，你希望它接下来检查什么，而不是继续盲改？
- 首先应该停止无依据的重复修改，检查失败是否出现了新信息，并重新建立问题假设。
- 
    1. 对比三次测试日志，确认报错是否发生变化。
    
    2. 检查具体失败的断言和预期结果。
    
    3. 重新读取相关实现、调用方与依赖。
    
    4. 检查是否修改了错误的位置。
    
    5. 查看 Git diff，判断修改是否引入了新问题。
    
    6. 必要时回退到稳定状态，再采用另一种解决方案。
    

如果发现工具持续返回完全相同的错误、参数也没有变化，就应该触发无进展检测，而不是继续无限重试。



5. 什么情况下应该让代码执行计算或数据处理，而不是让模型直接给出答案？
- 当任务具备可形式化、需要高准确性、数据量较大或需要复现验证等特点时，优先考虑代码执行。
例如：
- 统计10000笔订单的销售额；
- 对复杂逻辑规则进行判断；
- 将相同模板批量生成几百份文档。

合理分工是：LLM 负责理解问题、建立计算逻辑；代码负责执行明确计算；验证程序和外部证据负责检查结果。
