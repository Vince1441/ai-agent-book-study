# Task 3 -- 工具

## 【学习内容】
1. 理解 Tools 是 Agent 与外部世界交互的“手脚”，认识感知、执行、协作、事件触发、用户沟通五类工具。
    - Agent理解任务目标➡️决定调用哪个工具➡️观察结果➡️继续决策
    - 感知工具：读取与搜索信息；
    - 执行工具：修改外部状态；
    - 协作工具：委派与协调任务；
    - 事件触发工具：外部事件唤醒Agent；
    - 用户沟通工具：向用户回复，发送通知与状态反馈；
  可以从两个特征来审视他们，
    1. 调用方向（此次交互由谁发起？）
    2. 作用对象（这次交互作用于什么？）

2. 理解感知工具如何控制返回给 Agent 的信息量。
- 感知工具的核心：如何让Agent以尽量少的上下文成本，获取足够完成任务的信息；
- 三种控制信息量的方法：
    1. 结构化搜索结果
        作用：先返回候选，不返回全部原文；    示例：标题、路径、摘要
    2. 分页/游标
        作用：限制单次搜索结果数量；    示例：top_k=10,next_cursor;
    3. 区间读取/显式截断
        作用：按照所需读取文件的一部分；    示例：offset=100，limit=200

3. 理解执行工具中的权限、安全与风险控制。
- “执行—验证—反馈”的闭环
    1. 参数验证：格式是否合法？是否有注入、路径遍历？
    2. 权限判断：是否允许访问外部目标资源？
    3. 风险审批：是否涉及删除、付费等高风险动作？
    4. 实际执行：在受限环境中运行并记录结果
    5. 结果验证：检查状态、实际完成内容或执行后的行为
    6. 反馈与修复：返回结构化成果，必要时请求人工介入


4. 了解协作工具如何支持 Agent 与子 Agent 之间的任务协作。
- 协作工具的价值为：让一个Agent不必承担所有任务；
- 主Agent可以通过创建子Agent（spawn_subagent），通过消息工具补充要求，通过状态工具获取结果，最终在任务取消时终止子Agent；
- 子Agent的prompt应该写清楚角色、信息来源、任务边界与输出格式；
- 子Agent的形式可采取：同步等待、异步任务、流式进度、多轮协作等不同形式；

5. 理解工具描述、参数设计与接口设计为什么会影响 Agent 的使用效果。
- ACI（Agent-computer Interface）关注怎么设计方便Agent使用的接口，要求我们站在模型的角度去思考：
    - Agent能否判断什么时候应该调用工具？
    - 能否知道此工具的能力边界；
    - 能否准确填写参数？
    - 能否理解返回的结果？
    - 能否在失败后正确恢复？

- 原始工具描述：
  search：搜索相关内容
- 返回ACI描述理念：模型根本无法根据这段文字描述而去判断怎么调用、什么时候调用、它能搜索什么内容（能力边界）、接受什么输入（怎么填写参数）、结果返回什么？（理解返回的结果）
- 根据工具描述，可增写为：
- {
  "name": "search_documents",
  "description": "在已授权的本地知识库中搜索文档内容。适用于用户询问已上传文档中的事实。不适用于实时网络新闻或文件修改。",
  "parameters": {
    "query": {
      "type": "string",
      "description": "搜索问题，例如：退款申请期限"
    },
    "top_k": {
      "type": "integer",
      "minimum": 1,
      "maximum": 20,
      "default": 5
    }
  },
  "returns": {
    "results": "包含文档ID、标题、片段和来源位置的列表",
    "next_cursor": "用于继续分页的游标，可为空"
  }
}

可以得出结论：
  优秀的工具描述至少回答六个问题：能做什么、何时使用、何时不用、参数怎么填、返回什么、失败如何处理。




6. 了解 MCP 的 Client / Server 基本结构，以及不同 Agent 与工具之间的标准化连接。
- MCP Client：
    - 建立连接
    - 发现工具及参数
    - 发起标准调用
    - 接受工具结果

- MCP Server：
    - 暴露可用能力
    - 声明接口schema
    - 执行服务端操作
    - 返回数据或错误

不同Agent框架共用相同的适配接口，去调用同一个工具

7. 理解 MCP 中 Tools、Resources、Prompts 三种能力的区别。
- Tools：模型可以调用的操作
    示例：查询数据库、创建文件、发送消息；
- Resources：应用可以获取的数据
    示例：文档内容、数据库记录、配置信息；
- Prompts：可复用的提示词模板
    示例：代码审查模板、报告生成模板；

Tools是做事干活、Resources是获取资料信息、Prompts是提供做事时可以使用的提示词模板；


8. 了解大量工具场景下的主动工具发现与按需加载思路。
根据“不管工具能力做成什么形态，一次该让模型看见多少”，有三类解决思路：
    1. 层次化组织与按需加载：
        先看到目录，真正需要时在加载获取某个工具的完整Schema
    2. 主动工具发现：
	    Agent发现自己缺失能力，再调用工具搜索，根据需求定位合适的MCP Server和具体Tool
	3. Skills渐进式披露：
		    默认只保留少量名称与描述，需要用到时再读取具体流程、脚本和参考资料



## 自测题目
1. “读取文件”和“删除文件”都是操作文件，为什么设计重点不同？
- “读取文件”和“删除文件”虽然同为操作文件，但是类型不同；
- “读取文件”为感知工具，主要关注的设计重点为：
    读取文件的效率、上下文的消耗、获取信息的完整性；
- “删除文件”为执行工具，运行会改变实际的系统文件状态，可能造成不可逆的数据丢失
    需要规范验证目标路径与权限、判断文件是否允许删除、对重要删除操作要求人工确认、提供审计记录以及必要的恢复机制、验证删除结果等；
因此，不能一概而论都是操作文件，就采用相同的设计方式、设计重点。


2. 一个工具描述只有“搜索相关内容”，你会补充哪些信息？调用条件
    - 调用条件；供模型清楚任务过程中，什么时候调用、怎么调用工具；
    - 能力边界；供模型知晓此工具能够完成什么，不能做什么；
    - 参数格式；供模型知晓如何填写精确参数
    - 返回值与具体示例；供模型理解返回的结果
- 本质上让模型不但知道“工具能做什么”，还知道“什么时候不该使用它”

3. 工具返回“执行成功”，是否足以说明用户的任务已经完成？
- 不足以说明用户的任务已经完成，工具反馈成功、操作成功、用户目标成功，是三个不同的判断标准；还需验证：
    - 内容是否与用户预期一致
    - 生成的内容是否存在语法和类型错误；
    - 程序是否能真正运行成功；
    - 是否满足用户提出的功能要求；


4. MCP 的 Client 和 Server 分别承担什么职责？Tools、Resources、Prompts 各适合表达什么？
- Client是负责使用MCP协议与服务端交互的客户端组件；
- Server是提供标准化能力的服务端；

- Tools：提供于模型可调用的操作；
- Resources：提供于模型可读取的数据；
- Prompt：提供于模型可复用的提示模板；


5. 发送邮件的工具超时了，为什么不能直接重试？你会先确认什么？
- 工具超时只能说明客户端没有在预期时间内收到结果，并不能表示邮件没有发出；
- 邮件可能已经成功提交到服务端，但响应丢失了，如果再次发送，然后继续触发超时，可能会造成用户收到数量庞大的重复邮件；
- 应该检查：
    - 此次发送操作的请求ID
    - 邮件服务端的提交状态
    - 是否已生成消息ID
    - 是否存在可确认的发件记录
    - 服务端是否支持基于幂等键的安全重试
  确认第一次发送的邮件没有发生，或者能够利用幂等机制避免重复副作用后，再进行重试


6. 工具从 10 个增加到 1000 个时，全部提供给模型可能带来什么问题？
- 主要有四个方面的问题：
    1. 上下文成本：大量Schema，每次组建context的过程中消耗大量token；
    2. 工具选择错误：相似的工具描述过多，模型容易混淆；
    3. 缓存效率下降：动态工具定义可能会导致KV Cache失效；
    4. 安全与维护成本：工具来源、权限、安全和描述更难统一管理；
- 解决方法：层次化组织、按需加载、Skills渐进式披露
