# Task 10 -- 多Agent协作

## 综合概述

1. 理解 Single-Agent 与 Multi-Agent 的区别及适用场景。

- 用户布置任务：“调研三个产品的参数信息，并生成一份对比报告”
- Single-Agent：
	适用场景：
	 用户任务
	 ⬇️
	 Single-Agent（规划、搜索、阅读、分析、编写报告、检查，多项按顺序进行）
	 ⬇️
	 最终对比报告

- Multi-Agent：
	适用场景：
	 用户任务
	 ⬇️
	Reasearchr A （调研工具 A）
	Reasearchr B （调研工具 B）
	Reasearchr C （调研工具 C）
	Reasearchr D （调研工具 D）
	Reviewer 核实调研返回的数据事实
	Manager 汇总结果
	- 其中多个调研工具可并行工作，最终仍需统一汇总及验证成果

- 区别：

| **维度** | Single-Agent     | Multi-Agent          |
| ------ | ---------------- | -------------------- |
| 决策主体   | 一个主要Agent        | 多个Agent              |
| 上下文    | 相对集中，只服务于单个Agent | 可以共享、亦可隔离            |
| 分工     | 单个Agent按顺序依次进行   | 不同Agent承担不同任务        |
| 调试     | 执行链相对简单、直观       | 需要跨Agent跟踪状态消息       |
| 成本     | 通常较低             | 通信、协调与模型API调用开销，普遍更高 |
| 典型优势   | 简单、直观、易于维护       | 隔离上下文、并行搜索、专业分工      |
- **Multi-Agent并不一定优于Single-Agent**：当多个 Agent 只是围绕同一段文本重复讨论，且没有引入新信息时，Multi-Agent效果未必优于使用相同计算预算的Single-Agent。



2. 学习多 Agent 中的角色设计，理解任务拆解、角色分工和结果汇总。
- 三类协作拓扑：

| 拓扑                  | 控制方式               | 适用情况           |
| ------------------- | ------------------ | -------------- |
| 对等协作 Peer           | Agent之间相互反馈        | 生成-审核、辩论、头脑风暴  |
| 管理者模式 Orchestration | Manager 统一规划、分派和汇总 | 多步骤、有依赖、需要动态调度 |
| 去中心化 Decentralized  | Agent自主协商和移交       | 开发环境、动态伙伴与任务变化 |






3. 了解 Agent 之间的信息传递与协作，理解典型工作流，例如 Planner → Researcher → Executor → Reviewer。
- 以一个具体任务设计协作系统：“调研三款AI Coding工具的官方功能、适用场景和限制，并最终生成一份附上来源的对比报告”。
- 协作系统角色职责表：

| Agent      | 接受什么          | 负责什么             |
| ---------- | ------------- | ---------------- |
| Planner    | 用户需求、预算、评价维度  | 拆解任务、分配工作、确定验收标准 |
| Researcher | 调研范围、问题清单     | 搜索资料并核对来源、准确度    |
| Executor   | 已确认的数据参数、报告模板 | 整理比较、计算、生成报告     |
| Reviewer   | 报告、原始来源、验收标准  | 独立检验报告、发现遗漏或错误   |
	用户提出任务需求
	⬇️
	Planner：
	生成调研计划、任务ID及确认验收标准
	⬇️
	Researcher A
	Researcher B
	Researcher C
	各自独立进行搜索资料、调研数据
	⬇️
	Executor
	合并已检验数据、根据模板生成对比报告
	⬇️
	Reviewer
	对照来源检查报告，验证模版要求





4. 区分共享上下文与独立上下文，认识不同的任务组织和调度方式。
- 共享上下文（继承式协作）：
	Agent A：需求分析
	
	⬇️继承前序完整轨迹
	
	Agent B：代码实现
	
	⬇️继续继承历史
	
	Agent C：代码审查
	
	- 优势：历史细节保留完整。
	- 问题：轨迹持续增长，后续角色可能受到大量无关历史干扰。

- 独立上下文（隔离式协作）：
	Agent A                   Agent B                     Agent C
	↕️
	共享文件与结构化消息
	只交换必要的任务输出、产物和状态
	
	 - 优势：上下文更精简、隔离性更好。
	 - 问题：需要明确通信格式、同步机制与任务交接。



5. 思考什么时候应该使用多 Agent，什么时候单 Agent 就足够，并关注通信、协调和失败处理带来的成本。
- 基本依据：协作是否带来了有效的信息增量，以及收益是否足以覆盖额外的计算和协调成本。
- 不同任务该如何选择：

| 任务               | 更适合的模式       | 原因                  |
| ---------------- | ------------ | ------------------- |
| review一段python代码 | Single-Agent | 任务简单，额外协调成本不必要      |
| 修改一个简单函数并测试      | Single-Agent | 一个闭环足够              |
| 翻译一本长篇技术手册       | Multi-Agent  | 技术术语统一、章节翻译、审核内容可分离 |
| 搜索多个竞品信息         | Multi-Agent  | 可并行运作提高效率           |

- 通信、协调和失败处理所带来的成本：
	 核心判据：协作是否带来了有效的信息增量，以及收益是否足以覆盖额外的计算和协调成本。
	1. 通信成本：任务输入与结果需要明确转换、传递和解析。
	2. 协调成本：Manager 需要管理依赖、进度和调度。
	3.  一致性成本：多个 Agent 可能持有不同版本的事实。
	4. 验证成本：必须辨别哪个结果正确，不能简单投票。
	5.  故障恢复成本：超时、取消、部分成功都需要单独处理。



 ## **自测问题**

1. 把一个提示词拆成四个角色，是否就一定比单 Agent 更好？
- 不一定。如果四个角色使用相同模型、相同上下文，仅仅把同一个问题重复讨论四遍，可能只是增加了 Token 消耗。
- 真正有价值的多 Agent 分工，需要至少具备明确的职责边界，能够通过独立工具、外部证据、专业分工或者并行探索带来增益。
- 例如，Reviewer 只是说“我再仔细检查一次”，不如让它运行真实测试并读取失败日志。
- 因此，衡量架构不能只看角色数量，而应比较相同预算下的任务完成率、质量、延迟和成本。


2. 共享上下文与独立上下文，各可能出现什么信息管理问题？
- 共享上下文可能导致历史轨迹膨胀、无关信息干扰当前角色，以及角色之间难以形成独立视角。
- 独立上下文则可能造成信息遗漏、摘要失真、状态不同步、重复工作及调试困难。
- 前者重点解决信息过载，后者重点解决交接和一致性问题。


3. 多个 Agent 共享一个文件夹，是否等于它们共享完整对话上下文？
- 共享文件夹属于数据交换机制，只能让 Agent 读取对方保存的文件。
- 完整对话上下文还包含角色指令、历史消息、工具调用及执行轨迹等信息。
- 即使双方访问同一个共享文件，也不代表它们拥有彼此的全部上下文。


4. Reviewer 只阅读结果，与实际运行测试或核查来源，有什么区别？
- 前者主要依靠模型已有知识判断内容是否合理。后者引入了独立证据。
- 例如，Reviewer 阅读代码可能认为逻辑正确，但运行测试后却发现实际返回500错误。
测试结果是新信息，能够帮助识别单纯阅读无法可靠发现的问题。


5. 一个子 Agent 超时，或两个 Agent 给出矛盾结论时，主 Agent 应该如何处理？
- 一个子Agent超时，应检查状态、进度和副作用，随后根据预算取消、重试、重新分派或升级人工处理，并尽可能保留已确认成果。
- 两个Agent同时给出矛盾结论，应回到原始证据，核对来源、时间和适用条件；必要时安排独立验证，不能简单相信第一个报告成功的 Agent。
- 两种情况下，Manager 都需要保留可追踪的状态记录，并明确何时停止自动恢复。


6. 请分别举出一个适合多 Agent 和一个更适合单 Agent 的任务，并说明理由。
- **多Agent(Multi-Agent)：翻译一本几百页的技术书。**
因为术语提取、分章节翻译、全文审校具有不同职责，章节翻译还可以并行进行。独立上下文能降低各角色的信息负担，统一术语表和审校机制则帮助保证一致性。

- **单Agent(Single-Agent)：修改一个 Python 函数中的简单计算错误。**
一个 Agent 使用读取、编辑、执行测试等工具就能形成完整闭环。拆成 Planner、Coder、Tester、Reviewer 四个独立 Agent 可能增加通信延迟，而收益有限。
